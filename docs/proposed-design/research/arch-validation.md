# Research report: architecture validation (2026-09-25)

Produced by a research subagent on 2026-09-25 from web sources. Reproduced as received, lightly joined from three messages. Verify anything load-bearing before relying on it.

## A. "Event log + per-channel renderers + single active responder" — PARTIAL

The pattern is not named anywhere, but every major framework implements the two primitives it needs: (1) inject text/system items into a live voice session and (2) rebuild a session's context from external state. None ships a cross-session "floor" arbiter or a text-agent/voice-agent switch for the same user. That layer is always application code.

- **LiveKit Agents**: text arriving on the `lk.chat` stream during a voice session "interrupts its current speech, if any, to process the message and generate a new response." Manual injection is `session.generate_reply(user_input=...)`. Each `AgentSession` "begins with an empty chat context" that you populate before start, so prior history is your responsibility. Handoffs pass context explicitly. https://docs.livekit.io/agents/multimodality/text/ , https://docs.livekit.io/agents/build/external-data/ , https://docs.livekit.io/agents/logic/workflows/
- **Pipecat**: `LLMMessagesAppendFrame(..., run_llm=True)` is the injection primitive, but open issue #3829 reports that in speech-to-speech pipelines (OpenAI Realtime, Nova Sonic) a `send-text` message only interrupts and "the text is not sent to the LLM and no response is produced." Injecting text into a Realtime-backed Pipecat pipeline is not reliable today. https://github.com/pipecat-ai/pipecat/issues/3829
- **OpenAI Agents SDK**: `RealtimeSession.sendMessage()` (JS) and `session.send_message()` (Python) inject typed input and by default trigger a response. Realtime handoffs swap instructions/tools on the same session and "the new agent automatically has access to the ongoing conversation history." No mechanism bridges a text `Agent` run with a `RealtimeSession`; connect resets history to empty. https://openai.github.io/openai-agents-js/guides/voice-agents/build/ , https://openai.github.io/openai-agents-python/realtime/guide/
- **Vapi**: the closest built-in to server-side event injection. The `controlUrl` accepts `add-message` with `role` (system/user/assistant) and `triggerResponseEnabled`, plus `say` and `end-call`. This is exactly the "labeled conversation item, with urgency flag" primitive. https://docs.vapi.ai/calls/call-features
- **ElevenLabs Agents**: distinguishes `user_message` (interrupting, with `source_medium` text/audio) from `contextual_update` ("inject into the conversation without interrupting", with `context_id` supersession). Also a `text_only` override. Matches the urgency flag split. https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket
- **Retell**: separate voice agents and chat agents built from one agent definition; continuity across a call and a chat is via `retell_llm_dynamic_variables` on Create Chat, not shared history. https://docs.retellai.com/api-references/create-chat

Verdict: the "inject labeled items into the live session" half is standard (Vapi, ElevenLabs, LiveKit, OpenAI SDK all do it). The "single source of truth outliving the session, rendered per channel" half is what every framework leaves to you, and the OpenAI demo repo's chat-supervisor pattern (realtime agent fronting a text model) is the nearest published precedent. https://github.com/openai/openai-realtime-agents

## B. OpenAI Realtime API current state — CONFIRMED with caveats

Note: platform.openai.com/docs now 301-redirects to developers.openai.com/api/docs.

- **Server-side control**: create the call server-side with an API key via `POST https://api.openai.com/v1/realtime/calls` (browser SDP offer in, answer out). The `Location` response header is `/v1/realtime/calls/rtc_...`; extract the call_id and attach a sideband WebSocket at `wss://api.openai.com/v1/realtime?call_id={callId}`. Over the sideband the server can send `session.update`, receive and answer tool calls, and monitor all events. `POST /v1/realtime/calls/{call_id}/hangup` "can be used to terminate both SIP and WebRTC realtime sessions." Accept/reject/refer are SIP only. Client secrets for the browser come from `POST /v1/realtime/client_secrets`. https://developers.openai.com/api/docs/guides/realtime-server-controls , https://developers.openai.com/api/docs/guides/realtime-sip , https://developers.openai.com/api/docs/guides/realtime-webrtc
- **Sideband credential caveat**: between 2026-09-09 and 2026-09-14 a bug broke sideband attach when the call was created with an ephemeral client secret (404 call_id_not_found). The pattern that kept working throughout is: API key creates the call, the same API key opens the sideband. Use that. https://community.openai.com/t/ephemeral-keys-trigger-realtime-sideband-404-errors/1396002
- **session.update mid-session**: allowed "at any time to update any field except for voice and model"; voice can change only before the first audio output. Instruction changes "won't apply to responses already in progress." Clear a field with "" / [] / null. https://developers.openai.com/api/reference/resources/realtime/client-events , https://developers.openai.com/api/docs/guides/realtime-conversations
- **conversation.item.create + response.create**: items accept `previous_item_id` for placement ("root" for beginning). "Only one Response can write to the default Conversation at a time." A second `response.create` while one is active is rejected with `invalid_request_error`, code `conversation_already_has_active_response`, and is dropped, not queued. Out-of-band responses (`"conversation": "none"`) can run in parallel. `response.cancel` ends the active one with `response.done` status `cancelled`. https://community.openai.com/t/realtime-api-server-response-error-message-conversation-already-has-an-active-response/1005582
- **Limits**: hard maximum 60 minutes per session, after which the server sends a `session_expired` error and closes the socket. Optional `idle_timeout_ms` under `turn_detection.server_vad` emits `input_audio_buffer.timeout_triggered` and triggers a model response. https://developers.openai.com/blog/realtime-api , https://community.openai.com/t/realtime-api-session-timeout-post-ga/1357331
- **Transcription and disconnect**: user audio transcripts arrive as `conversation.item.input_audio_transcription.delta` and `.completed`, keyed by `item_id`; "ordering between completion events from different speech turns isn't guaranteed." Enable via `audio.input.transcription.model`. There is no `realtime.call.ended` webhook; the only realtime webhook is `realtime.call.incoming` (SIP). Disconnect detection is yours: sideband WebSocket close, browser `connectionstatechange`, or a heartbeat. The JS SDK `connection_change` event is reported unreliable on connection loss. https://developers.openai.com/api/docs/guides/realtime-transcription , https://github.com/openai/openai-agents-js/issues/613
- **Models and modalities**: `gpt-realtime` (snapshot 2025-08-28) is superseded by `gpt-realtime-2` (May 2026) and `gpt-realtime-2.1` plus a 2.1 mini (July 2026); `gpt-realtime-mini-2025-12-15` also exists. The quickstart now uses `gpt-realtime-2.1`. The beta Realtime API was removed 2026-05-12. `output_modalities: ["text"]` is still supported for text-only output. https://developers.openai.com/api/docs/changelog , https://developers.openai.com/api/docs/guides/realtime
- **Sideband drops after silence**: if the WebRTC session is quiet for longer than the ping-response timeout, the sideband websocket drops and needs re-establishing. https://community.openai.com/t/side-band-websocket-connection-to-webrtc-call-for-gpt-realtime-api-drops-out-after-period-of-silence/1368689

## C. OpenAI Agents SDK (JS) — CONFIRMED / PARTIAL

- `RealtimeSession.sendMessage(message, otherEventData)` sends typed input into the live session and triggers a response by default. `updateHistory()` diffs local history and sends delete/create events (function-call items cannot be edited). `updateAgent()` and handoffs apply a new session config on the same connection; "input filters are currently not applied."
- `connect()` resets history to an empty array; there is no initial-history option. Seeding prior thread context is done after connect via `updateHistory`. Python has `session.send_message()` and `realtime_handoff()`.
- No supported bridge exists between text Agent runs / Session memory and a RealtimeSession in JS or Python. The primitives exist; the pattern is left to you.

## D. Google OAuth for Gmail — CONFIRMED

- (i) In production with only openid/email/profile: "available to any user with a Google Account"; the unverified-app warning appears only "if your project's OAuth clients request authorization of scopes considered sensitive or restricted." Brand verification is only needed to show a logo/display name. https://support.google.com/cloud/answer/15549945 , https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification
- (ii) `gmail.readonly`, `gmail.metadata`, `gmail.compose` are Restricted; `gmail.send` is Sensitive; `gmail.labels` is Non-sensitive. Restricted scopes need CASA security assessment, recertified every 12 months, "can potentially take several weeks." https://developers.google.com/workspace/gmail/api/auth/scopes , https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification
- (iii) Testing status: max 100 test users; "authorizations by a test user will expire seven days from the time of consent." Exception: apps requesting only name/email/profile need no test-user list and do not expire. Also a 100-refresh-token cap per account per client. https://developers.google.com/identity/protocols/oauth2

## E. Poke / Persona public descriptions — UNKNOWN

- Poke (Cognition acquired it July 2026) is publicly text-only: Apple Messages, Telegram, WhatsApp, RCS, voice notes. The OpenPoke write-up describes an interaction agent plus persistent execution agents with a 100-message summarization threshold, no voice channel. https://poke.com/docs , https://www.shloked.com/writing/openpoke , https://cognition.com/blog/interaction
- Persona (yourpersona.com) publishes no architecture. Toyo ("lives in iMessage and calls your phone") reports Cloudflare Durable Objects plus a realtime voice framework, i.e. a per-user actor holding shared state, consistent with this design. https://yourpersona.com/ , https://www.producthunt.com/products/toyo

## Implications for the design

- Create every WebRTC call server-side with the API key and open the sideband with the same key.
- Serialize `response.create` per session with a one-slot queue: `response.cancel` for urgent events or defer until `response.done`. Never fire blind.
- Non-urgent injected events should be system items without `response.create`, matching ElevenLabs contextual_update and Vapi add-message with triggerResponseEnabled false.
- Log voice turns keyed by `item_id`, not arrival order.
- Call-end detection needs three sources: sideband socket close, client `connectionstatechange`, and the 60-minute `session_expired`. Plan a reconnect path before 60 minutes for long calls.
- Seed the Realtime session with prior history by creating conversation items after connect; instructions alone will not carry the thread.
- Target `gpt-realtime-2.1` (or its mini for cost).
- Gmail: ship production with openid/email/profile only. Keep `gmail.readonly` behind a Testing project with listed test users, and budget CASA before public launch.

## Addendum: Pydantic AI Realtime (checked separately, 2026-09-25)

Pydantic AI added realtime speech-to-speech support in August 2026 (OpenAI Realtime, Azure, Gemini Live, xAI Grok Voice behind one API). Relevant points: an offer-relay helper returns the SDP answer and a session handle, and the agent's realtime session attaches to it as the sideband; message history seeds the session via the same parameter as normal runs; `send()` injects text, `interrupt(played_ms=...)` cancels; transcripts stream as events. Caveats: dynamic instructions resolve once at connect, new tools cannot be added mid-session, provider resumption does not cross processes. Install `pydantic-ai-slim[openai-realtime]`. https://pydantic.dev/docs/ai/realtime/openai/ , https://pydantic.dev/docs/ai/realtime/overview/ , https://pydantic.dev/articles/pydantic-ai-voice-agent
